\large Preserving Task Success While Cutting Tokens and Staying Under Rate Limits}

\begin{abstract}
Tool outputs---web pages, JSON API responses, logs, CSV exports---are the
largest and most-ignored token sink in LLM agent loops. A single verbose tool
result can dwarf the agent's instructions, and the standard mitigation, blind
truncation, silently discards the fact the agent needs. We present \tooltrim, a
drop-in, provider-agnostic library that compresses tool outputs \emph{before}
they re-enter context using a content-type router and query-aware extraction,
while keeping the full output retrievable on demand via a content-addressed
store. We introduce the \emph{Tool-Output Faithfulness Benchmark} (\tofb), 66
cases that plant a checkable fact inside realistic, bloated tool output across
five content types, with single-fact, multi-fact, distractor, and aggregation
variants. On \tofb, query-aware compression retains \textbf{100\%} of
full-context accuracy while removing 94--99\% of tokens, whereas truncation
collapses to 2--14\% ($p<0.001$ at every budget by a paired McNemar test). We
report three findings: (i) compression can \emph{improve} accuracy---on Claude
Sonnet~5, compressing to 256 tokens raises accuracy from 73\% to 92\%
($p{=}0.001$)---by removing distracting tool-output noise; (ii) compression acts
as \emph{rate-limit admission control}---under a hosted provider's per-request
token cap, only 42\% of raw tool outputs are admissible versus 100\% of
compressed ones; and (iii) against strong query-aware RAG top-$k$, \tooltrim{}
ties on answer accuracy ($p\geq 0.48$ on three frontier models) but its output
stays \emph{machine-parseable}---the gold fact is recoverable from a real parse
57\% of the time versus 39\% for RAG, which shreds structured output into
fragments an agent cannot re-parse. We release \tooltrim{} (PyPI, MIT), the \tofb{} dataset (HuggingFace), and
a reproducible baseline harness comparing \tooltrim{} against truncation, RAG
top-$k$, and LLMLingua-2.
\end{abstract}

\section{Introduction}
Autonomous LLM agents interleave reasoning with tool calls: they fetch a web
page, query an API, grep a log, read a table. The \emph{output} of each call is
appended to the context window and carried forward for the rest of the episode.
These outputs are routinely enormous---a rendered HTML page is tens of thousands
of tokens of navigation, scripts, and boilerplate wrapping a single fact; a
paginated JSON response is hundreds of near-identical records. Left unmanaged,
tool outputs dominate the context budget, inflate cost and latency, push the
relevant signal past the model's effective attention span, and---on hosted
providers with per-request token caps---get the call rejected outright.

The prevailing fix is to truncate: keep the first or last $N$ tokens. This is
cheap and catastrophic---the needed fact is as likely to sit in the middle as at
either end, and truncation has no notion of \emph{what the agent asked for}. We
argue the right operation is \emph{query-aware, faithful compression}: shrink the
output using the agent's current goal as a relevance signal, exploit the
structure of each content type, and keep the discarded remainder retrievable so
compression is lossless in expectation rather than a gamble.

\paragraph{Contributions.}
\begin{enumerate}
\item \tooltrim, a zero-dependency, provider-agnostic library that compresses
tool outputs via a content-type router (HTML/JSON/logs/tabular/text) and
query-aware BM25 (or optional embedding) extraction, with expand-on-demand over
a content-addressed store, exposed as a decorator, an OpenAI/Anthropic-compatible
proxy, framework adapters (LangChain, LlamaIndex, OpenAI-Agents), and an MCP
gateway.
\item \tofb, a reproducible 66-case faithfulness benchmark with a single
checkable gold fact per case across five content types and four difficulty
modes (single-fact, multi-fact, distractor, aggregation), released on HuggingFace.
\item An honest, paired-significance evaluation against truncation, RAG top-$k$,
and LLMLingua-2, plus a frontier-model accuracy/token Pareto---and a
\emph{downstream-extractability} metric that measures whether a compressed output
still parses in code, the axis on which content-type structure separates
\tooltrim{} from plain query-aware selection.
\item Three findings with practical weight: compression as an accuracy aid (even
for a frontier model), compression as provider rate-limit admission control, and
parity-on-recall but structural separation (machine-parseable output) against RAG
top-$k$.
\end{enumerate}

\section{Related Work}
\textbf{Prompt compression.} LLMLingua and LLMLingua-2~\cite{jiang2023llmlingua,
pan2024llmlingua2} compress prompts by dropping low-information tokens under a
target ratio, learned from a smaller model. They operate on free text and are
content-type agnostic; \tooltrim{} instead routes by content type and is
query-aware and lossless-on-demand. \textbf{Retrieval.} RAG~\cite{lewis2020rag}
selects passages relevant to a query; we include a BM25 top-$k$ RAG baseline and
find it a strong competitor, which we discuss directly. \textbf{Long context and
the ``lost in the middle'' effect}~\cite{liu2024lost} motivates removing
mid-context filler rather than assuming models attend to everything.
\textbf{Agent frameworks and MCP.} Tool use is standardized by function calling
and the Model Context Protocol; \tooltrim{} plugs in at that boundary rather than
requiring agent rewrites.

\section{Method}
\subsection{Content-type router}
Given a tool output, \tooltrim{} detects its type (HTML, JSON, logs, tabular,
prose) and applies a type-specific compressor: HTML is stripped to salient text,
JSON/tabular are field- and row-pruned, logs are deduplicated and severity-
ranked. Each compressor emits candidate chunks that preserve local structure.

\subsection{Query-aware extraction}
The agent's current goal is the relevance query. Chunks are scored---BM25 by
default, or a pluggable embedding scorer---and greedily packed to a token budget,
keeping each selected chunk's immediate neighbors for context. Because the query
is exactly what the agent is trying to accomplish, the surviving text is the part
the model actually needs.

\subsection{Expand-on-demand}
The full, uncompressed output is written to a content-addressed store
(file/Redis/S3) and referenced by a short id embedded in the compressed result.
An \texttt{expand} tool returns any region on request, so no information is
permanently lost---compression degrades gracefully to retrieval.

\subsection{Deployment surfaces}
\tooltrim{} is a decorator (\texttt{@compressed\_tool}), an OpenAI/Anthropic-
compatible \emph{proxy} that requires zero agent code changes and fails open,
framework adapters, and an MCP gateway that compresses at the protocol boundary.
The proxy exposes Prometheus metrics (tokens in/out, savings, fail-open events).

\section{The Tool-Output Faithfulness Benchmark (\tofb)}
\tofb{} isolates the property that matters: does the needed fact \emph{survive}
compression? Each of 66 cases plants one distinctive fact (a ``needle'') inside a
large, type-appropriate tool output and pairs it with a question whose wording
overlaps the needle. Filler is generated deterministically (seeded, and reseeded
on every dataset build), so cases are fully reproducible from source---bit-for-bit
across processes---and contain no scraped or personal data. Cases span five content
types (text, HTML, JSON, logs, tabular) and four modes: \textbf{single} (50; one
fact), \textbf{multi} (6; two facts placed far apart, both required),
\textbf{distractor} (6; a similar-but-wrong value sits far from the right one; the
answer must appear and the trap must not), and \textbf{aggregation} (4; several
records match the query and all must be recovered---a structural ceiling for
top-$k$ selectors). Mean output size is $\approx$6.8k tokens/case ($\approx$450k
tokens total). Scoring is
unambiguous: a case passes iff the model's answer contains the gold string
(normalized), all \texttt{all\_of} facts appear, and no \texttt{must\_not}
distractor appears. \tofb{} is released on HuggingFace under MIT.

\section{Experimental Setup}
We evaluate with two judges. The \textbf{offline} judge is a deterministic BM25
retrieval model that answers correctly iff the needed fact survived
compression---a no-API control that isolates the compressor. The
\textbf{real-LLM} judge sends the same prompt to a hosted model; answers are
disk-cached so reruns never re-spend tokens. We compare \tooltrim{} against
\emph{full context}, \emph{truncate-head/tail}, \emph{RAG top-$k$} (BM25 chunk
selection), \emph{RAG-embed}, and \emph{LLMLingua-2}~\cite{pan2024llmlingua2} on
identical cases and budgets. Accuracies carry 95\% Wilson intervals; method
pairs are compared with a paired \textbf{McNemar} test on discordant cases.

\section{Results}
\subsection{Faithfulness vs. truncation (offline judge)}
Table~\ref{tab:baselines} reports retention (accuracy $\div$ full-context
accuracy). Query-aware methods retain \textbf{$\geq$100\%} of accuracy while
cutting 94--99\% of tokens---\tooltrim{} exceeds 100\% because removing filler
recovers facts the raw context buried even from the BM25 judge---whereas blind
truncation drops the fact and collapses (significant at every budget,
$p<0.001$).

\subsection{Real-LLM pilot and the \tooltrim{} vs. RAG question}
We ran a real-LLM pilot on Llama-3.3-70B (Groq), $n=8$ (the full-context baseline
is the token hog and must stay under the free-tier cap). Query-aware $\gg$
truncation holds and is significant even at $n=8$ (McNemar $p=0.023$--$0.041$).
However, RAG top-$k$ edged \tooltrim{} 8/8 vs.\ 7/8 at the 256- and 800-token
budgets---\emph{not} significant ($p=1.0$). Whether \tooltrim's content-type
structure separates it from plain query-aware selection under a strong judge is
therefore an open question: on single-needle recall the offline lexical judge ties
them almost by construction (both keep the one needle). We resolve it with a
frontier-model matrix and a structural metric.

\subsection{Frontier accuracy/token Pareto}
\texttt{run\_frontier.py} runs the full grid across frontier models on the same
cases and budgets, emitting a cross-model Pareto and the paired \tooltrim-vs-RAG
McNemar test per model. Table~\ref{tab:pareto} reports a full $n{=}66$ run across
three frontier models from two providers (Claude Haiku 4.5, Claude Sonnet 5, and
OpenAI GPT-4o-mini); the matrix extends to further providers (Groq, local Ollama)
with the corresponding API keys.

\paragraph{Compression beats full context and truncation.} On Claude Sonnet 5,
uncompressed tool output yields only 73\% accuracy, but compressing it to 256
tokens \emph{raises} accuracy to 92\% (retention 127\%; McNemar $p{=}0.001$ vs.\
full, and significant at every budget)---the full-context noise actively degrades
a capable model, and removing it recovers the answer. On Claude Haiku 4.5, full
context is already strong (97\%) and compression holds or improves it (100\% at
256 tokens, retention 103\%). Against truncation, \tooltrim{} wins by 60--89
points at every budget on all three models ($p<0.001$).

\paragraph{Against RAG: parity on recall, separation on structure.} On
answer accuracy \tooltrim{} and query-aware RAG top-$k$ are statistically
indistinguishable: they stay within $\pm 3$ points and the difference is
\emph{not} significant on any of the three models at any budget ($p\geq 0.48$). This
confirms the pilot---single planted facts reward any query-aware selector
equally, so raw recall cannot separate the two. The separation is instead
\emph{structural}. Because \tooltrim{} respects each content type, its compressed
output is still \emph{valid for the agent's next step}: on the JSON/tabular cases
its result parses in code and the gold fact is recoverable from that parse
(\emph{downstream-extractability}) 57\% of the time at a 256-token budget, versus
39\% for RAG top-$k$, which shreds single-line JSON into mid-object fragments an
agent cannot \texttt{json.loads}. This holds identically on all three models---the
metric is deterministic, computed from the compressed text, not the judge---and
at every budget (Table~\ref{tab:pareto}). RAG's fragments \emph{happen} to answer
a natural-language question because a strong LLM reads around the broken syntax;
they fail the moment the agent's next tool call tries to parse them. That is the
axis on which content-type structure pays off.

\paragraph{Budget as a cap, not a target.} A design detail matters here. An
earlier array selector filled its record quota up to whatever the budget allowed;
because keyword-stuffed distractors score just above zero, a \emph{larger} budget
re-admitted them and lowered accuracy as the budget grew---at the 800-token budget
it fell below RAG top-$k$. We replaced the fill-to-quota rule with a
\emph{relevance cliff}: keep only records scoring at least half of the best
match's score. Single-needle queries then keep just the needle; genuine
multi-record (aggregation) queries keep the whole high-scoring cluster; and
accuracy no longer decays with budget (95/92/92\% across the three budgets on
Sonnet, the parity reported above). The budget is a ceiling on what may be kept,
never a quota that must be filled---the principle that let \tooltrim{} match RAG
top-$k$ at every budget rather than trailing it at the largest.

\subsection{Compression as an accuracy aid}
Removing tool-output noise \emph{raises} accuracy, and not only for small
models. In cross-model runs, compression to a 128-token budget improved accuracy
from 13\% to 84\% (Mistral-7B) and 23\% to 73\% (Llama-3.1-8B), with
non-overlapping Wilson intervals. The frontier run above shows the same effect on
a capable model with statistical significance: Claude Sonnet 5 rises from 73\% to
92\% ($p{=}0.001$). Less, on-topic context beats more, noisy context --- the
excess is not merely wasted budget, it degrades the answer.

\subsection{Compression as rate-limit admission control}
Under Groq's per-request token cap, only \textbf{42\%} (28/66) of \emph{raw} tool
outputs are admissible---the rest are rejected---versus \textbf{100\%} of
compressed outputs. A live proxy A/B turned a 14{,}415-token rejected call into a
26-token accepted one that answered correctly. Compression is thus not only a
cost lever but an \emph{availability} mechanism: it keeps agent calls inside
provider limits.

\section{Systems and Scalability}
\tooltrim{} ships an async proxy with a pluggable content-addressed store
(file/Redis/S3) and Prometheus metrics. A horizontal load test (Kubernetes +
shared Redis; \texttt{k8s/}) measures throughput (RPS), p50/p99 latency, and
compression overhead under concurrency, and reports tokens---and dollars---saved
across a realistic agent workload. Because the store is content-addressed,
replicas share expansions and scale horizontally without coordination.

\section{Limitations}
On \emph{answer accuracy}, \tooltrim{} and RAG top-$k$ tie: the offline lexical
judge ties them by construction, and the frontier matrix ($n{=}66$) removes that
construction yet the tie persists ($p\geq 0.48$ on all three models). We read this as a
property of the metric---single planted facts in homogeneous filler reward any
query-aware selector equally, and a strong LLM reads around broken syntax to
answer a natural-language question. The separation we do measure is
\emph{structural}: because \tooltrim{} preserves content-type validity, its output
remains machine-parseable and the gold fact stays recoverable from a real parse
(downstream-extractability 57\% vs.\ 39\% for RAG), which is what an agent's
\emph{next} tool call actually depends on. Whether that structural advantage
converts into higher end-to-end agent-task success---where a broken \texttt{json.loads}
halts the loop rather than merely making one answer harder to read---is the
natural next evaluation, on an existing agent benchmark rather than fact recovery
alone. \tofb{} uses synthetic, deterministically generated outputs for
reproducibility and to avoid PII; a companion track drawing cases from real agent
traces is future work.

\section{Conclusion}
Tool outputs are the dominant, least-managed token sink in agent loops.
Query-aware, faithful compression preserves---and for small models improves---task
success while cutting the overwhelming majority of tokens and keeping calls inside
provider rate limits. We release the library, the \tofb{} benchmark, and a
reproducible baseline harness so the result is easy to check and build on.
